# users-svc

The second microservice of the news app. It owns user accounts and profiles
and exposes them over a versioned REST API. Login, passwords and tokens are
out of scope; they belong to a future auth service.

## Layout (clean architecture)

```
app/
├── domain/models.py            # User entity + business rules. Depends on nothing.
├── application/
│   ├── ports.py                # UserRepository interface, StorageUnavailable
│   └── use_cases.py            # UserService: list, get, create, update
├── infrastructure/
│   ├── postgres_repository.py  # PostgreSQL adapter (used when DATABASE_URL is set)
│   └── json_repository.py      # JSON file adapter (used when DATABASE_URL is not set)
├── api/
│   ├── schemas.py              # Public API contract (request + response models)
│   ├── routes.py               # /api/v1/* endpoints
│   └── health.py               # /health/live, /health/ready
├── config.py                   # Settings from environment variables
├── logging_setup.py            # JSON logs to stdout
└── main.py                     # Composition root: wires layers together
migrations/versions/            # Alembic migrations: the users table schema, in order
alembic.ini                     # Alembic config (the URL comes from DATABASE_URL)
data/users.json                 # 5 seed users (4 active, 1 disabled); SEED_FILE for Postgres
tests/                          # Unit tests (no deps) + API tests (FastAPI) + Postgres/migration tests
```

Dependencies point inward: `api → application → domain`, and
`infrastructure` implements the `application` port.

## Data model

| Field | Type | Notes |
|---|---|---|
| id | string (UUID) | Generated by the service; referenced by `articles-svc` as `author.id` |
| email | string | Unique, stored lower-cased; compared case-insensitively |
| display_name | string | 1–100 characters, trimmed |
| status | enum | `active`, `disabled` |
| created_at, updated_at | ISO-8601 datetime (UTC) | `updated_at ≥ created_at`; bumped on every change |

## Endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/users` | List, newest first. Query: `status`, `q` (email/name search, 2+ chars), `page`, `page_size` |
| GET | `/api/v1/users/{id}` | One user |
| POST | `/api/v1/users` | Create. Body `{email, display_name}` → **201** + `Location` header |
| PATCH | `/api/v1/users/{id}` | Partial update. Body: any of `{email, display_name, status}` |
| GET | `/health/live` | Liveness probe |
| GET | `/health/ready` | Readiness probe (503 if data failed to load) |
| GET | `/docs` | Interactive Swagger UI (auto-generated) |

Request bodies reject unknown fields (e.g. `password`) with a 422.

Errors always look like:
```json
{ "error": "conflict", "message": "Email 'a@b.co' is already registered", "request_id": "..." }
```

| Status | `error` | When |
|---|---|---|
| 404 | `not_found` | Unknown user id |
| 409 | `conflict` | Email already used by another user |
| 422 | `validation_error` | Bad email, blank/long name, unknown field, empty PATCH, bad enum |
| 503 | `storage_unavailable` | The database is unreachable, or the write could not be persisted |

## Run it

**With Docker (recommended):**
```bash
docker compose up --build
# open http://localhost:8081/docs
curl -X POST localhost:8081/api/v1/users \
  -H 'content-type: application/json' \
  -d '{"email":"asha@example.com","display_name":"Asha"}'
curl -X PATCH localhost:8081/api/v1/users/<id> \
  -H 'content-type: application/json' -d '{"status":"disabled"}'
```

Compose starts, in order:
1. `users-db`: its own Postgres (database per service).
2. `users-migrate`: a one-shot job from the same image that runs
   `alembic upgrade head` and exits. It shows as `Exited (0)` in
   `docker compose ps -a`; that's expected.
3. `users-svc`: starts only if the migrations succeeded. On first connect,
   because `SEED_FILE` is set, it loads the 5 seed users into the empty table.

Data lives on the named volume `users-db-data`, so it survives `restart` and
`down`/`up`. To reset to the seed data, run `docker compose down -v`.

The database publishes no host port. To look inside:
```bash
docker compose exec users-db psql -U users -c "SELECT email, status FROM users"
```

If the database goes down, users-svc stays up: `/health/ready` returns 503 and
requests return `503 storage_unavailable` until it is back.

**Without Docker:**
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8081
```
Without `DATABASE_URL` this uses the JSON file adapter and writes to
`data/users.json` itself. Use `DATA_FILE=/tmp/users.json` (with a copy of the
seed) to keep it clean. The JSON adapter is for **a single replica only**.

## Test it

```bash
python -m unittest discover -s tests -p "test_use_cases.py"   # no dependencies
pytest                                                        # all tests, needs requirements-dev.txt
```
Tests work on temporary copies of the seed file, so they never modify it.

The Postgres adapter and migration tests need a throwaway database (they drop
the tables and run the migrations from scratch) and are skipped without one:
```bash
docker run --rm -d --name users-test-db -e POSTGRES_PASSWORD=test -p 55432:5432 postgres:17-alpine
TEST_DATABASE_URL=postgresql://postgres:test@localhost:55432/postgres pytest tests/test_postgres_repository.py
docker stop users-test-db
```

## CI and images

`.github/workflows/ci.yml` runs on every push:
1. `test`: `pytest` with a Postgres service container (`TEST_DATABASE_URL` set), so the
   Postgres and migration tests run too.
2. `image`: builds the image, smoke-tests it (`/health/ready` must return 200 with the
   bundled JSON data), then pushes it to GHCR. Runs only if `test` passed.

Images are `linux/arm64` only (built natively on ARM runners; the server is AWS Graviton). Images are public: `docker pull ghcr.io/ankurvapte/users-svc:<full commit SHA>`.
Every pushed commit gets its own SHA tag, which never changes; pushes to `main` also
move `:main`. Deploy by pinning a SHA tag, never `:main`.

## Change the schema

The schema lives only in `migrations/versions/`, applied in order and recorded
in the `alembic_version` table. Never edit a migration that has been deployed;
add a new one:
```bash
alembic revision -m "add last_login_at to users" --rev-id 0002   # no database needed
# write the SQL in upgrade() and downgrade() with op.execute(...)
docker compose up --build                                         # users-migrate applies it
```
Expand, then contract: every migration must keep both the old and the new
app version working (add a nullable column first, make it required in a later
migration), so deploys and rollbacks stay safe. Adding a column also means
updating `postgres_repository.py` and this README's data model.

## Configuration (environment variables)

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | *(unset)* | Postgres connection URL. Set → Postgres adapter; unset → JSON file adapter. Also used by `alembic upgrade head` |
| `SEED_FILE` | *(unset)* | JSON file loaded into an empty `users` table on first connect (Postgres only) |
| `DATA_FILE` | `data/users.json` | JSON adapter's data file (read and written) when `DATABASE_URL` is unset |
| `LOG_LEVEL` | `INFO` | Log verbosity |
| `DEFAULT_PAGE_SIZE` | `10` | Page size when none is given |
| `MAX_PAGE_SIZE` | `50` | Upper bound on `page_size` |
| `PORT` | `8080` | Container listen port (host port 8081 in compose) |
| `SERVICE_NAME` | `users-svc` | Name stamped on every log line |
